# Telegram и MAX

Реализованы два адаптера к общей бизнес-логике кабинета. Это текстовые боты:
создание заявок, общий чат, переписка по заявке, история сообщений, согласование
актуальной оценки в часах, уведомления и настройки каналов.

Заказчик регистрируется на сайте. Сотрудники работают в веб-кабинете и получают
уведомления со ссылкой на конкретную заявку или чат. Денежные операции,
голосовые сообщения и вложения в эту версию не входят; бот явно сообщает,
если присланное вложение не было обработано.

## Подключение к реальным мессенджерам

1. Получите токен Telegram-бота через BotFather и токен MAX-бота через инструменты
   платформы MAX. Укажите реальные публичные ссылки на обоих ботов.
2. Разверните кабинет на публичном HTTPS-домене. Для MAX нужен порт 443.
3. Установите переменные из `.env.example` в окружении веб-сервера **и** worker.
   `.env` автоматически не загружается. `APP_DB` должен указывать на один и тот же
   абсолютный путь в обоих процессах. Можно подключить сначала один мессенджер.
4. Для каждого бота сгенерируйте отдельный webhook-секрет. Команда:
   `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
   Требуется 32–128 символов из букв ASCII, цифр, `_` и `-`.
5. Запустите веб-сервер за HTTPS reverse proxy:
   `python -m uvicorn app:app --host 127.0.0.1 --port 8000`.
6. Зарегистрируйте адреса получения событий:
   `python bot_worker.py register`.
   Для одного провайдера: `python bot_worker.py register --provider telegram`
   или `--provider max`. Команда не удаляет накопленные события Telegram.
7. Запустите доставку: `python bot_worker.py run`. Поддерживается фильтр
   `--provider telegram` / `--provider max`. Процесс должен постоянно работать.
8. Войдите в кабинет → **Мессенджеры** → **Подключить**. Скопируйте команду
   `/link …`, отправьте её своему боту и введите полученный код подтверждения
   на сайте. До подтверждения бот не получает доступ к данным кабинета.

Для Windows используйте абсолютный Windows-путь в `APP_DB` и задавайте переменные
через `$env:ИМЯ = 'значение'` в PowerShell до запуска каждого процесса.
На сервере запускайте веб и worker через менеджер процессов с перезапуском при
сбоях. Секреты храните в защищённом окружении; не передавайте токены в аргументах
командной строки и не добавляйте их в репозиторий.

Внешние адреса:

- `POST /webhooks/telegram` — проверяет `X-Telegram-Bot-Api-Secret-Token`.
- `POST /webhooks/max` — проверяет `X-Max-Bot-Api-Secret`.

Используется MAX API `https://platform-api2.max.ru`, токен передаётся в заголовке
Authorization. Если среде требуется дополнительный доверенный сертификат,
подготовьте CA bundle и задайте `BOT_CA_BUNDLE`. Проверка TLS не отключается.
Источники: [Telegram Bot API](https://core.telegram.org/bots/api),
[MAX: webhooks](https://dev.max.ru/docs-api/methods/POST/subscriptions),
[MAX: отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages).

## Правила работы

### Запуск MAX вместо Telegram

Существующий адаптер MAX выполняет те же клиентские сценарии на общей базе кабинета.
Задайте `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `MAX_BOT_URL`, `APP_PUBLIC_URL`
и общий `APP_DB` в окружении веб-приложения и worker. Telegram для этого не требуется.

```powershell
python -m bot.worker register --provider max
python -m bot.worker check --provider max
python -m bot.worker run --provider max
```

`check` проверяет доступ к API и подписку на нужные события, не отправляя сообщений.
`webhook_not_registered` означает, что нужно выполнить `register`;
`webhook_missing_event_types` — перерегистрировать подписку;
`api_401` — проверить токен; `network_or_invalid_response` — соединение и доверенные сертификаты.
Успешная проверка подписки не подтверждает доступность нашего сервера со стороны MAX:
после запуска обязательно отправьте боту `/start`, привяжите кабинет и создайте тестовую заявку.

Для переноса уведомлений подключите MAX в разделе «Мессенджеры» и выберите MAX
основным каналом уведомлений. Вторая привязка сама по себе не меняет выбранный Telegram.
Заявки и переписка сохраняются в кабинете, коды подключения отправляйте новому боту.
В Docker запуск только MAX: `docker compose --profile bots run --rm bot-worker python -m bot.worker register --provider max`,
затем аналогично `check`; для постоянной доставки задайте команду сервиса worker
`["python", "-m", "bot.worker", "run", "--provider", "max"]` и запустите профиль `bots`.

MAX требует публичный HTTPS webhook; долгий опрос предназначен только для разработки
и тестирования ([документация MAX](https://dev.max.ru/docs-api/methods/GET/updates)).

- `/start`, `/help` — меню; `/cancel` — отмена текущего ввода; `/settings` —
  канал уведомлений. Меню также завершает текущий ввод.
- Одна учётная запись мессенджера привязывается к одному кабинету. У кабинета
  может быть по одной привязке Telegram и MAX. Код подключения одноразовый,
  действует 10 минут; код подтверждения приходит только в личный диалог бота.
- Первая привязка становится основным каналом уведомлений. Второй канал не
  включает дублирование автоматически. Пользователь может выбрать оба или
  полностью отключить внешние уведомления. После удаления привязки выбор
  переключается на оставшуюся, если удалённый канал использовался.
- Бот работает только в личных диалогах. Имя пользователя не является
  идентификатором доступа. На каждом действии проверяются активность учётной
  записи и доступ к заявке или чату.
- Тема → описание → проверка → отправка. До отправки можно изменить поля или
  отменить заявку. Черновики отдельные для каждого бота, хранятся 24 часа;
  созданные заявки общие для обоих ботов и сайта.
- Ответ на сообщение бота отправляется в связанный с ним диалог. Во время
  создания заявки и корректировки оценки ввод относится к текущему сценарию.
  Кнопка «Ответить» выбирает диалог для следующего сообщения. Без ясного
  контекста бот сохраняет текст и предлагает выбрать общий чат либо заявку.
- История показывается по пять сообщений, заявки — по восемь с переходом
  к следующей странице. Полная история доступна в кабинете.
- Одобрение и отклонение оценки требуют подтверждения конкретной версии.
  При корректировке можно предложить часы или оставить только комментарий.
  Повторное решение и старая версия не изменяют данные. Одобрение часов не
  создаёт списания денег.
- События из веба сохраняются в той же транзакции, что и очередь доставки.
  Собственные сообщения не возвращаются пользователю как новые уведомления.
- Отключение привязки удаляет её черновики, кнопки и ещё не отправленные
  сообщения. Перед отправкой повторно проверяются доступ и настройки.
  Уже отправленные сообщения остаются в истории мессенджера.

## Доставка и диагностика

Входящее событие, изменение заявки, состояние диалога и ответ фиксируются в
одной SQLite-транзакции. Повторный webhook не повторяет бизнес-операцию.
Кнопки содержат случайные идентификаторы, привязанные к владельцу, и действуют
семь дней; подтверждения дополнительно проверяют текущую версию и состояние.

Worker использует аренду задания на 60 секунд, ограничивает отправку в один
диалог примерно одним сообщением в секунду, повторяет временные ошибки с
увеличением интервала и учитывает `retry_after`. После десяти попыток задание
помечается `failed`; ошибки неверного запроса и блокировки прекращают повторы
раньше. При блокировке бота доставка этой привязке останавливается до нового
входящего события от пользователя. Callback подтверждается отдельным
приоритетным заданием. Для первой версии рекомендуется один worker.

- `python bot_worker.py status` — количество заданий по провайдеру и состоянию.
- `python bot_worker.py retry-failed` — повтор сообщений после устранения
  причины ошибки; права и настройки будут проверены заново.
- Логи содержат номер задания, провайдера и код ошибки без текстов переписки
  и токенов. Не включайте HTTP debug-логи в production: Telegram использует
  токен в URL API.
- Делайте резервные копии общей SQLite-базы. Очередь, привязки, черновики и
  ключи защиты от повторной обработки находятся в ней же.

Если провайдер принял исходящее сообщение, а соединение оборвалось до получения
ответа, повтор может доставить копию сообщения. Внешние API не дают общей
транзакции с нашей базой. Это не приводит к повторному созданию заявки или
повторному решению по оценке.

## Проверка

`python -m unittest discover -s tests -v`

Проверяются оба входных формата, привязка и отзыв доступа, шаги создания и
редактирования, повторные и конкурентные события, адресация ответа, согласование
между мессенджерами, корректировка, уведомления, секреты webhook, ограничение
размера запроса, повторная доставка, восстановление аренды и HTTP-адаптеры.
Тесты используют отдельные временные базы и подменённые HTTP-ответы провайдеров.

До рабочего запуска нужно провести проверку с реальными токенами и HTTPS:
привязать оба бота, создать заявку, ответить из кабинета, согласовать оценку,
отключить канал и проверить прекращение доставки. Автотесты эту проверку
не заменяют.
