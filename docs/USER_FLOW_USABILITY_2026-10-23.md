## Воспроизводимые дефекты

### UX-01 · P1 · Клиент видит внутренние имена сотрудников

- **Где:** список заявок и общий чат заказчика; подтверждено также в снимках участника и наблюдателя компании.
- **Повторить:** войти владельцем → «Мои заявки» → посмотреть колонку ответственного; открыть общий чат.
- **Факт:** показаны «Исполнитель разработки», его инициалы, «Менеджер продаж». Это имена тестовых сотрудников, а не единый контакт поддержки.
- **Последствие:** нарушено описанное в README правило скрытия личности исполнителя. Сам профиль сотрудника сообщает, что заказчик общается с «Службой поддержки».
- **Исправить:** единое представление автора/ответственного для заказчика, включая список, чат, цитаты, поиск и ответы API. Повторно проверить с индивидуальными именами и аватарами.
- **Доказательства:** [список](../output/ux-audit-current/customer-staff-list.png), [чат](../output/ux-audit-current/meeting-message-date.png), `usability.json → customer-staff-privacy`, `confirm.json → pendingRow`.

### UX-02 · P2 · В приглашении на встречу показана техническая дата UTC

- **Повторить:** сотрудник → встречи → отправить ссылку клиенту → клиент → общий чат.
- **Факт:** сообщение содержит `Время: 2026-10-24T01:03:00+00:00`.
- **Последствие:** клиенту приходится самостоятельно понимать формат и прибавлять три часа для Минска; возможна ошибка со временем встречи.
- **Исправить:** показывать «24 октября, 04:03 (Минск, UTC+3)» либо локальное время с явно указанным поясом. Проверить переход через полночь.
- **Доказательство:** [сообщение встречи](../output/ux-audit-current/meeting-message-date.png), `details.json → meetingMessage`.

### UX-03 · P2 · Ссылка на видеовстречу в чате не кликабельна

- **Повторить:** открыть отправленное клиенту сообщение со ссылкой на встречу.
- **Факт:** URL отображается обычным текстом; среди ссылок DOM чата есть только вложения. Ссылки `https://meet.example.test/audit-room-v4` среди них нет.
- **Последствие:** вместо перехода одним нажатием нужно выделять и копировать адрес, особенно неудобно с телефона.
- **Исправить:** безопасное распознавание HTTP(S)-адресов в сообщениях; для встречи — отдельная кнопка «Подключиться».
- **Доказательства:** [сообщение](../output/ux-audit-current/meeting-message-date.png), `confirm.json → links`.

### UX-04 · P2 · Непринятая работа названа завершённой

- **Повторить:** сотрудник сдаёт работу → клиент открывает список заявок до приёмки.
- **Факт:** у заявки №6 одновременно «На проверке» и «Завершена» в колонке ближайшего срока. Сводка считает 4 завершённых, хотя закрытых только 3; четвёртая ещё ожидает приёмки. В карточке правильно предлагается принять или вернуть работу.
- **Последствие:** список сообщает, что процесс окончен, хотя от клиента требуется действие.
- **Исправить:** для `done` показывать «Ждёт вашей приёмки», для `closed` — «Завершена»; явно определить, что считается завершённым в сводке.
- **Доказательства:** [строка списка](../output/ux-audit-current/pending-row.png), [карточка приёмки](../output/ux-audit-current/review-customer.png), `confirm.json → pendingRow/card`.

### UX-05 · P2 · Несохранённый профиль теряется без предупреждения

- **Повторить:** профиль заказчика → ввести телефон → перейти в заявки без сохранения → вернуться в профиль.
- **Факт:** введённое значение исчезает, предупреждения нет. В проверке поле вернулось к пустому значению; диалогов — 0.
- **Последствие:** пользователь теряет введённые данные. Поведение отличается от формы заявки и чата, где черновики сохраняются.
- **Исправить:** сохранять черновик профиля либо предупреждать об уходе; явно показывать наличие несохранённых изменений. Проверить также профиль сотрудника отдельно.
- **Доказательство:** `usability.json → profile-unsaved`.

## Замечания по удобству и текстам

### UX-06 · P2 · На телефоне поиск и заявки находятся ниже первого экрана

- **Условия:** владелец компании, 375×812, две карточки «Ждём от вас».
- **Факт:** верх поиска — примерно y=1140, первой заявки — y=1287. До рабочего списка приходится прокручивать больше экрана. Сводки занимают основное место.
- **Улучшить:** компактные или сворачиваемые сводки на телефоне; поиск и быстрые фильтры ближе к заголовку. Блоки с необходимым действием сохранить заметными.
- **Доказательства:** [первый экран](../output/ux-audit-current/mobile-list-top.png), `details.json → mobileTicket`.

### UX-07 · P2 · Покупка обещает зачисление часов при денежном депозите

- **Повторить:** клиент → биллинг → «Купить пакет часов».
- **Факт:** форма обещает «Часы поступят на баланс». По README учёт ведётся в рублях, часы — эквивалент по текущему тарифу; изменение тарифа не сохраняет фиксированное количество часов.
- **Последствие:** покупатель может ожидать право на фиксированные 10 часов, хотя фактически пополняет денежный депозит на 30 000 ₽.
- **Улучшить:** написать «На депозит поступит 30 000 ₽ — эквивалент 10 часов по текущему тарифу»; одинаково объяснять покупку, баланс и счёт.
- **Доказательства:** [форма покупки](../output/ux-audit-current/billing-dialog.png), `details.json → purchaseText`, раздел README «Администрирование и денежный депозит».

### UX-08 · P3 · В мобильном чате нужно отдельно прокручивать страницу до формы ответа

- **Условия:** 375×812, открытие существующего общего чата.
- **Факт:** переписка прокручена к последним сообщениям, но форма ответа находится ниже видимой области и нижней навигации. Для доступа к ней требуется дополнительно прокрутить страницу примерно на 200 px. После прокрутки форма и кнопка доступны: блокировки отправки не обнаружено.
- **Улучшить:** размещать компактную форму ответа над нижней навигацией и рассчитывать высоту истории от доступной области экрана. Проверить с открытой экранной клавиатурой на устройстве.
- **Доказательства:** [после открытия](../output/ux-audit-current/mobile-chat-1.png), [после прокрутки](../output/ux-audit-current/mobile-chat-bottom.png), `edges.json → mobileChat`.

## Что прошло

- 108 переходов по разделам десяти профилей: личный клиент, владелец, участник, наблюдатель, исполнитель, проверяющий, менеджер, продажи, финансы, администратор.
- 20 адаптивных проверок главных экранов при 768 и 375 px; дополнительно восемь клиентских разделов при 375×812. Переполнения документа по ширине не выявлено. Визуально просмотрены ключевые клиентские экраны и мобильный экран сотрудника финансов.
- Сквозной цикл новой заявки №11: создание → назначение → оценка → цена менеджера → корректировка → повторная оценка → согласование → внесение времени → сдача → возврат → доработка → приёмка. Две версии оценки, 90 минут работы, итог `closed`.
- Счёт на 30 000 ₽ → подтверждение оплаты → акт на 7500 ₽; баланс после операций 29 000 ₽ с учётом исходного состояния копии базы.
- Ставка исполнителя → подтверждение записи → акт → отметка выплаты. Исполнитель видит свой оплаченный акт; селектора другого сотрудника нет.
- Отправка ссылки на встречу увеличила число сообщений клиента с 13 до 14. Отмена встречи сохранила запись в истории.
- Ввод поиска CRM/встреч не теряет фокус. Запоздалый ответ чата не уводит из профиля. Сохранение срока в админке не сдвигает время: 12:00 UTC → 15:00 Минск → 12:00 UTC.
- Черновик новой заявки сохранил тему, описание, тип, приоритет и видимость. Поиск и фильтр списка восстановились после возврата. Черновик общего чата пережил переход/перезагрузку.
- Самостоятельная регистрация, ошибка входа и повтор с верным паролем прошли. Запрос восстановления показал нейтральное сообщение; получение письма и активация ссылки не проверены.
- Окно покупки после завершения анимации закрывается по Escape. Раннее подозрение на проблему не подтвердилось и в список дефектов не включено.

В навигационном прогоне ошибок JavaScript не было. Три первоначальных 404 относились к изображению из скопированной базы без каталога вложений. Каталог перенесён в тестовую копию; повторная проверка подтвердила загрузку изображения. Это ошибка подготовки стенда, в дефекты продукта не включена.

## Границы

Реальные банковские платежи, внешняя доставка email/Telegram/MAX и системных push не проверялись. На стенде фоновые задания отключены, почта не настроена; восстановление доступа нельзя считать пройденным сквозным сценарием. Для рабочего развёртывания доставка писем требует отдельной проверки. Прогон выполнен в браузере, без физических устройств и экранной клавиатуры. Все комбинации дополнительных прав, все операции справочников и полный WCAG-аудит не покрыты. С утверждённым визуальным эталоном сравнение не выполнялось. Существующий полный набор unit-тестов в этом аудите не запускался.

Машинные результаты, сценарии и скриншоты: `output/ux-audit-current/`. Контекст7 вернул превышение месячной квоты; браузерный Chrome MCP — занятый профиль, CUA — тайм-аут. Для фактического прогона использован отдельный Edge через установленный Playwright и существующие сценарии проекта.
