# Архитектура

Проект разделён на веб-приложение и интеграцию с мессенджерами.

`payroll.py` реализует внутренние выплаты исполнителям через `/api/payroll`, отдельно от клиентского биллинга. `payroll_sources` связывает записи фактической работы, оценки и сопровождения с решениями и актами. Положительные ID сохранены для работы, отрицательные нечётные ID обозначают оценки, отрицательные чётные — сопровождение; исходные таблицы могут иметь совпадающие ID без коллизий. Миграция прежнего учёта работы сохраняет подтверждения и акты. `payroll_rates` хранит историю ставок в центах USD/час, `payroll_reviews` — текущее решение по записи времени, `payroll_audit` — историю решений. `payroll_acts` и `payroll_act_items` хранят неизменяемый состав акта. Уникальность `entry_id` исключает включение одной записи в несколько актов; `BEGIN IMMEDIATE` сериализует подтверждение и создание акта. Повтор создания с тем же ключом возвращает исходный акт, другой состав с тем же ключом отклоняется. Сравнение предварительной суммы защищает от устаревшего расчёта. `web/payroll.js` загружается по требованию при открытии раздела.

```text
app.py                 HTTP API, доменная логика и SQLite-сервисы
company_chat.py        общий чат организации, участники и миграция личных диалогов
team_management.py     функции, области доступа, команды клиентов, задачи, встречи, сделки и передача обязанностей
mailer.py              почта: SMTP/файл, разбор входящих ответов, IMAP
web_push.py            push-уведомления браузеров (VAPID)
bot/
  providers.py         Telegram/MAX: конфигурация, нормализация и доставка
  routes.py            pairing, настройки и webhook-эндпоинты
  service.py           единый сценарный движок бота
  storage.py           SQLite-схема состояния бота
  worker.py            отдельный durable worker очереди доставки
tests/
scripts/
web/
```

`app.py` остаётся точкой входа веб-сервера (`uvicorn app:app`). Бот не дублирует бизнес-правила: `bot.service.BotEngine` получает веб-приложение как domain adapter и вызывает его сервисы для заявок, чатов, оценок и прав доступа.

Webhook-обработка выполняется внутри веб-процесса через `bot.routes`, а отправка исходящих сообщений вынесена в отдельный процесс `python -m bot.worker run`. Это позволяет перезапускать worker независимо от API и повторять доставку через SQLite outbox.

Корневые файлы `bot_*.py` сохранены как тонкие compatibility-shim для старых импортов и тестов. Новый код должен импортировать модули из пакета `bot`.

Фоновые задачи веб-процесса (`background_jobs` в `app.py`) раз в 20 секунд отправляют письма из очереди `email_outbox`, раз в 10 минут в рабочие часы напоминают клиентам о незавершённых шагах, первого числа рассылают ежемесячную сводку и, если настроен IMAP, забирают ответы на письма. Повторы безопасны: напоминания и сводки отмечаются в базе, входящие письма — по `Message-ID`, поэтому несколько процессов не дублируют отправку.

## Запуск

```powershell
uvicorn app:app --reload
python -m bot.worker run
```

В Docker worker запускается отдельно профилем:

```powershell
docker compose --profile bots up --build
```


## Управление командой

`team_management` устанавливает `/api/team` через доменный адаптер приложения. Нормализованные таблицы `staff_functions`, `client_team`, `ticket_participants`, `task_participants` и `meeting_participants` хранят назначения; `staff_settings` — область доступа, разрешения и доступность. Функции не связаны с выдачей прав. Миграция старых `team_role` выполняется при первом создании настроек сотрудника.

`team_tasks`, `team_meetings` и `team_deals` имеют версии для защиты от устаревших сохранений. Передача сделки атомарна и защищена уникальным `team_tasks.deal_id`. Отдельный журнал `team_audit` сохраняет назначения, изменения и публикации. Передача обязанностей вызывается внутри существующей транзакции отключения/замещения сотрудника.

Опубликованные итоги встречи представлены совместимой записью `service_entries` с `is_billable=0`: существующие клиентские ленты и уведомления показывают только публичные итоги. Финансовые выборки исключают такие записи; удаление и изменение через API сопровождения запрещены. Все старые записи сопровождения при миграции получают `is_billable=1`.

`web/team.js` реализует рабочее пространство команды, адаптивные формы и редактирование назначений. SSE-событие `team_updated` не содержит содержимого записей: браузер получает данные заново через проверку области доступа. Открытая форма сохраняет введённые данные; конфликт версий возвращает HTTP 409.


## Таск-трекер

`task_tracker.py` подключает `/api/tasks` с теми же проверками видимости и записи, что и `team_management`. `TaskInput` допускает `customer_id=NULL`: внутренняя задача видна её создателю, исполнителю, проверяющему, участникам и пользователям разрешённой области. Клиентские задачи сохраняют прежнюю область доступа. Переходы, проверка чек-листа и принятие результата остаются в общем `save_work`, поэтому старый `/api/team/tasks` не обходит новые правила.

`task_checklist`, `task_comments`, `task_files` и `task_watches` связаны с задачей внешними ключами. Чек-лист имеет версии для конкурентного переключения пунктов. Создание задач, комментариев и загрузка файлов поддерживают ключи повторного запроса. Файлы размещаются в отдельном подкаталоге `ATTACHMENT_DIR/tasks`; скачивание проверяет видимость, принудительно использует Content-Disposition attachment и nosniff. Удаление файла в интерфейсе — обратимая отметка `deleted_at`.

`team_notifications.event_kind` различает назначения, упоминания, запросы проверки и существенные изменения. Непрочитанные события одного типа по одной задаче объединяются; уведомления проверяются по текущим правам. SSE передаёт только сигнал обновления, содержимое запрашивается заново через API. Простые комментарии не рассылаются всем участникам: уведомляются только упомянутые люди.

`web/tasks.js` реализует список, доску, быстрое создание, карточку и клавиатурные действия. Представления сохраняются в localStorage по ID пользователя; данные задач загружаются с сервера. `#tasks` и `#task/ID` поддерживают прямое открытие и историю браузера. Клиентский кабинет продолжает работать с заявками и не получает доступа к внутреннему таск-трекеру.

## Общий чат компании

`chats.organization_id` задаёт единый диалог организации; частичный уникальный индекс исключает дубликаты. Без организации сохраняется личный диалог аккаунта. Доступ участников проверяется по текущему составу `organization_members`, независимо от автора первого сообщения. Все роли компании могут писать в её чат; права на заявки остаются отдельными. Уведомления и SSE получают действующие участники компании, ответственный и диспетчеры.

`company_chat.init_schema` снимает старую уникальность по заказчику и объединяет прежние диалоги участников компании, сохраняя идентификаторы сообщений, вложения, уведомления и связи с заявками. `chat_aliases` направляет старые ссылки и контексты ботов в объединённый чат; новые идентификаторы не переиспользуют эти ссылки. При добавлении участника его прежний личный диалог присоединяется к чату компании при следующем обращении. История компании остаётся у неё после удаления участника.


## Клиентское ценообразование, проверка PM и скрытие часов от заказчика

Внутренняя оценка исполнителя отделена от коммерческого предложения клиенту:
1. **Черновик исполнителя (`pending_pm`)**: Исполнитель заявляет плановые часы (`performer_effort_minutes`) и время оценки. Оценка сохраняется в состоянии `pending_pm` и фильтруется на уровне API (`customer_record`, выборки активных оценок), поэтому клиент не видит черновики и не может их одобрить.
2. **Проверка и наценка PM (`/pm-review`)**: Диспетчер/PM принимает оценку, добавляет часы управления/QA (`pm_effort_minutes`), устанавливает итоговую стоимость (`custom_amount_rub` вручную или расчётом по почасовой ставке клиента `hourly_rate_rub`) и формулирует клиентское описание (`client_note`). Оценка переходит в состояние `pending` для заказчика.
3. **Скрытие часов от клиента**: Клиент видит исключительно общую сумму в рублях (`amount_rub`) и понятное описание. Внутренние часы исполнителя, часы PM и почасовая ставка скрыты из веб-интерфейса, ботов (Telegram/MAX) и почтовых уведомлений.
4. **Управление дополнительными часами (`/pm-decision`)**: Запросы исполнителя на допчасы поступают в `pending_pm`. Только PM принимает решение:
   - Внутреннее покрытие (`bill_customer=False`): утверждаются часы для исполнителя, клиент не привлекается и сумма не меняется.
   - Выставление клиенту (`bill_customer=True`): формируется запрос на доплату (`amount_rub`) с обоснованием от PM, клиент согласует сумму без раскрытия внутренних часов исполнителя.
